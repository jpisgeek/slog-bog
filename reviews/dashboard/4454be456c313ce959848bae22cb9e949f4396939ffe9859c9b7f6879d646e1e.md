## Checked and clean
1. Secrets/identifying info — searched all four files for credentials, tokens, keys, PEM blocks, cookies, hostnames, domains, IPs (private and public), MACs, serials, email addresses, vault/secret-store paths, local filesystem paths, and control characters in literals: nothing found beyond findings 1 and 8; all other defaults (`Operations`, `./dashboard/index.html`, `condition:accepted-maintenance`) are generic.
2. Credential handling — clean: no argument carries a secret (title/bundles/outputPath/suppress only), no vault access exists, no secret can reach logs, resources, or errors; both throw sites embed only `schemaVersion` and derived-state strings, and nothing is persisted to `.swamp/data` beyond the declared resources.
3. Transport and network — clean: zero network code (no fetch, WebSocket, or URL construction anywhere; README's no-network claim verified against every call site — only `Deno.mkdir` and `Deno.writeTextFile`), so TLS, hostname validation, scheme, timeout, and AbortSignal requirements are not applicable.
4. Untrusted input — see findings 2, 3, 4, 7; otherwise clean: every interpolation in `renderHtml` (text and quoted-attribute contexts, including `metric.reason`, `fact.value`, `suppressReason`, `coverage.scope`) passes through `esc()`, which escapes `& < > " '`; metrics use a discriminated union so unavailability cannot read as a numeric value; invalid bundles become critical coverage exceptions and zero bundles becomes a warning, so failure is never rendered as "all clear" (`allClear` requires ≥1 valid bundle, all healthy, no active exceptions); no bundle data reaches a shell, SQL, or file path.
5. Supply chain — clean: the sole import is `npm:zod@4` (the sanctioned bare-major platform exception); no other npm/jsr/https imports, no dynamic `import()`, no eval/`new Function`, nothing fetched at load time.
6. Documentation matches code — verified argument names, types, and defaults, the single `render` method with no arguments, both resource tables field-for-field against `RenderedExceptionSchema`/`RenderSchema`, lifetimes, version string across README/manifest/model, and the failure-behaviour caveats: all match; the only example drift is finding 1.
7. Data written — see list below and findings 5–6; README's Security section does warn that the rendered output inherits the sensitivity of the operational data it contains.

## Data written by this extension
- `exception` resources (lifetime infinite, GC 50): id, severity, subject, headline, detail, source, suppressed, suppressReason, truncated, plus tags severity/suppressed/source. Subject, headline, detail, and source are producer-supplied free text and may carry device names, hostnames, or other operational identifiers from upstream bundles; sensitivity classification is not carried (finding 5).
- `render` resource (lifetime infinite, GC 30): outputPath as configured (a local path), byte count, exception/suppression counts, bundle ids, per-bundle coverage states, exception resource names, renderedAt.
- Local file at `outputPath`: a self-contained HTML page containing every bundle's sections, metrics, facts, and exceptions — operational data whose exposure depends entirely on where the operator publishes the file.
