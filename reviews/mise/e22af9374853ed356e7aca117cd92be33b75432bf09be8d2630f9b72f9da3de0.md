| 1 | fix | mise/mise.ts:356 | Caller cancellation is misreported as a host failure. When `ctx.signal` aborts, `cmd.output()` throws, the catch classifies it via `classifyFailure(-1, msg)` → `"failed"`, and the worker writes the node as unmeasured with `failureKind: "failed"` — overwriting a previously good node record with a claim the host broke. The worker loop (`mise/mise.ts:781`) never checks `signal.aborted`, so a cancelled full sweep also churns every remaining node and writes a failure record for each. Section 3 requires cancellation not read as a remote failure. | `: classifyFailure(-1, msg)` | Detect abort (`signal.aborted` or `e.name === "AbortError"/"TimeoutError"` on the caller signal) before classifying; on caller abort, stop the worker loop and skip writing records for unswept nodes. |
| 2 | fix | mise/mise.ts:653 | Resource-name collision resistance rests on a 32-bit FNV-1a truncation. `identityKey` is injective, but the published name keeps only 8 hex chars of it. `slugPart` collapses punctuation runs, so a compromised host can vary punctuation in a tool name or config path (invisible to the slug) and search the trivial 2^32 space for a hash collision with another host's `tool-`/`config-` record, silently overwriting it in the shared write pass. The comment at `mise/mise.ts:644` claims "Collision-safe", which overstates what 32 bits deliver against an adversarial input. | `` `${prefix}-${flat \|\| "id"}-${fnv1a(identityKey(parts))}` `` | Use a longer digest (e.g. first 16 hex of SHA-256 over `identityKey`) or otherwise make the full identity part of the name; soften the comment to match. |
| 3 | note | mise/README.md:45 | Prune scope is under-documented. README says a full sweep "prunes tool and config records that have departed", but the prune loop deletes any record not written this sweep, including the `node` record of a host removed from config. | `A full sweep prunes tool and config records` | Say node records of departed hosts are pruned too. |
| 4 | note | mise/README.md:37 | `expect` only judges tools that appear in the host's current config. A host whose config never declares `node` records zero `expected` drift against `expect: {node: "22"}`, which a reader of "fleet-wide expectation" may take as the host passing. Absence of the tool is not disguised as a version match, but the doc does not state the limit. | `Optional fleet-wide expectation` | One sentence in README: expect applies only to tools the host's config declares; a tool absent from config is judged by `notinstalled`/`notineffect`, not `expected`. |

## Checked and clean
1. Secrets/identifying info: no credentials, keys, tokens, hostnames, IPs, secret-store paths, or local paths in any published file; disk scan for control characters/NUL bytes and for operator domains, private IP ranges, and `/Users|/home|/Volumes` paths found nothing; all examples use `example.com`, `/srv/project`, role-word node names; the operator's real name in LICENSE and the `jpisgeek` handle/repo URL are deliberate authorship identity, not leakage.
2. Credential handling: the extension carries no secrets — no vault use (`vaults: []`), no token/password arguments, SSH auth is ambient key/agent with `BatchMode=yes`; errors quote stderr only, truncated to 160 chars, stdout never reaches errors or logs; nothing persists a secret.
3. Transport: SSH and local exec only, no HTTP, no cleartext opt-out, host-key checking not weakened (BatchMode fails closed on unknown keys); every invocation has `ConnectTimeout` plus `AbortSignal.any` of caller signal and a hard timeout — cancellation is honoured but misreported, see finding 1.
4. Untrusted input: remote JSON is shape-checked before tolerant parsing (`isJsonPayload`), prototype-chain lookups on remote-controlled keys are guarded with `Object.hasOwn`, no HTML rendering; `dir`/`misePath` are rejected at parse time by strict charsets (`mise/mise.ts:22-27`) before interpolation, `user@host` is a single argv element with leading-dash refusal, local exec never touches a shell; failure is recorded as unmeasured/degraded with null counts, never as zero — except the collision edge in finding 2.
5. Supply chain: single import `npm:zod@4` (the sanctioned bare-major for the runtime-supplied zod), `dependencies: []`, no dynamic import, no eval/`new Function`, nothing fetched at load.
6. Docs match code: version, type name, all argument names/defaults/descriptions, the single `discover` method, all four resource schemas and lifetimes, the five subcommands listed in Security, the quoting description of `remoteCommand`, and the example config all verified against `mise.ts` — drift limited to findings 3 and 4.
7. Data written: reviewed below; README's Security section discloses that install and config paths embed home directories and project names.

## Data written by this extension
- `node` — operator-chosen host label, transport, the measured directory (real path, including the local working directory), mise version, and an error field carrying up to 160 chars of stderr (can include remote SSH error text such as auth-failure phrasing).
- `tool` — tool names/versions plus `installPath`/`sourcePath`, which embed the remote account's home directory and real project directory names (disclosed in README).
- `config` — mise config file paths per host (same home-directory exposure, disclosed).
- `summary` — aggregate counts and a sweep timestamp; no personal data.
- No MAC addresses, user lists, or credential material is written; stderr excerpts in `node.error` are the only free-text field sourced from a remote process.
